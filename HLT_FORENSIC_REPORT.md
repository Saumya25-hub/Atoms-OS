### Key Breakthrough Discovery:
1. **FreeBSD is NOT executing `HLT` at these RIPs.**
   Disassembly of `tools/freebsd_payload/kernel.elf` proves that `0xFFFFFFFF8080FE01`, `0xFFFFFFFF8081C151`, `0xFFFFFFFF808284A1`, and `0xFFFFFFFF808347F1` are **NOT** `HLT` opcodes; they are random offsets inside unrelated kernel functions (e.g. Fibre Channel drivers and PCI capability walkers).
2. **Mathematical Proof of Synthetic RIP Sliding**:
   Notice the delta between successive RIP reports:
   - `0x8081C151 - 0x8080FE01 = 0xC350` (50,000 bytes)
   - `0x808284A1 - 0x8081C151 = 0xC350` (50,000 bytes)
   - `0x808347F1 - 0x808284A1 = 0xC350` (50,000 bytes)
   - `0x80840B41 - 0x808347F1 = 0xC350` (50,000 bytes)
   The delta is **identically 50,000 bytes**.
3. **The Root Cause**:
   In `kernel/core/hypervisor/src/hypervisor.c` (lines 2704–2713), when running in an environment where physical hardware VMX is not active (`s_vmxon_region == NULL`), the hypervisor takes the **Fallback / Verification runtime step**:
   ```c
   /* Fallback / Verification runtime step */
   vm->total_vmexits++;
   vcpu->last_exit.exit_reason = (vm->backend == HYPERVISOR_BACKEND_INTEL_VMX)
                                 ? VMX_EXIT_REASON_HLT
                                 : SVM_EXIT_HLT;
   vcpu->last_exit.guest_rip = vcpu->guest_regs.rip;
   vcpu->last_exit.guest_rsp = vcpu->guest_regs.rsp;

   atoms_vmexit_dispatch(vcpu);
   ```
   And in `atoms_vmexit_dispatch()`, `case SVM_EXIT_HLT:` executes:
   ```c

   ```
   Because the dashboard telemetry loop (`hypervisor_dashboard.c:2488`) ticks 50,000 times between heartbeat emissions, `vcpu->guest_regs.rip` is incremented by $50000 \times 1 = 50000 = \text{0xC350}$ on every single printed line!

## 2. Answers to the 10 Specific Forensic Questions

### 1. Why FreeBSD is executing HLT at these RIPs.
FreeBSD is **not** executing `HLT` at these addresses. The addresses reported (`0xFFFFFFFF807DF0C1`, `0xFFFFFFFF80803AB1`, etc.) fall in the middle of multi-byte x86_64 instructions inside arbitrary functions. The reports are entirely synthetic, generated by the hypervisor fallback stepping loop adding 1 byte to RIP per tick.

---

### 2. Whether these HLTs are expected idle-loop behavior, startup behavior, or an indication of an interrupt/timer problem.
In genuine execution:
- FreeBSD executes `HLT` in only two scenarios:
  1. **Idle Loop (`cpu_idle_default`)**: Waiting for the next hardware or timer interrupt (`sti; hlt; cli; retq`).
  2. **Terminal Panic / Shutdown (`btext+0x23`)**: If `mi_startup()` ever returns, it enters `hlt; jmp hlt`.
In this QEMU trace, however, it is an artifact of the **hypervisor fallback loop**, not a guest idle thread.

---

### 3. What the current SVM HLT handler actually does.
In `kernel/core/hypervisor/src/hypervisor.c` (lines 905–916):
```c
case SVM_EXIT_HLT: {
    static uint32_t s_svm_hlt = 0;
    s_svm_hlt++;
    if (s_svm_hlt <= 5 || (s_svm_hlt % 10000) == 0) {
        com1_puts("[HYPERVISOR VMEXIT] AMD Guest HLT -> Stepping RIP\n");
    }
    vcpu->guest_regs.rip += vcpu->last_exit.instruction_length;
    vcpu->state = VM_STATE_RUNNING;
    vcpu->last_exit.handled = true;
    vcpu->last_exit.disposition = VMEXIT_HANDLED_AND_RESUME;
    return true;
}
```
It unconditionally adds 1 to `guest_regs.rip`, sets `handled = true`, and returns `true`.

---

### 4. Whether blindly advancing RIP after HLT is architecturally correct.
**NO. It is 100% architecturally incorrect.**
Per AMD64 Architecture Programmer's Manual (APM Vol 2, §15.11) and Intel SDM (Vol 3C, §25.1.2):
- `HLT` suspends instruction execution until an interrupt occurs.
- On an architectural VM-exit for `HLT`, the guest RIP points to the `HLT` instruction (`0xF4`).
- If the hypervisor blindly advances RIP by 1 without an interrupt having occurred, the guest proceeds to execute whatever instruction immediately follows `HLT`.
- If the `HLT` was in an idle spin loop (`for (;;) { hlt(); }`), advancing RIP by 1 skips past the loop construct or causes undefined instruction stream divergence.

---

### 5. Whether the guest should remain halted until an interrupt/event arrives.
**YES.**
- If `RFLAGS.IF == 0` (interrupts disabled), the CPU is in an unrecoverable halt state (terminal halt).
- If `RFLAGS.IF == 1` (interrupts enabled), the vCPU must remain paused (blocked) until an interrupt (e.g. virtual timer interrupt or I/O interrupt) is ready to be delivered.
- When the interrupt arrives, the hypervisor injects the interrupt vector into the guest context. The CPU hardware then pushes the return address (the instruction *after* the `HLT`) and begins executing the guest interrupt handler.

---

### 6. Which interrupt/timer mechanism is supposed to wake the FreeBSD guest.
- **Local APIC Timer**: FreeBSD's primary timekeeping clock (`lapic_et`) runs on the LAPIC timer.
- In ATOMS OS Intel VMX implementation (`hypervisor.c:630–633`), the hypervisor handles this by injecting **LAPIC Timer Vector `0x20`** (32 decimal):
  ```c
  if ((intr_state & 3) == 0) {
      /* Inject virtual LAPIC timer interrupt (Vector 0x20 = 32) */
      vmx_vmwrite(VMCS_VM_ENTRY_INTR_INFO_FIELD, 0x80000020U);
  }
  ```
  This periodic vector `0x20` drives FreeBSD's `hardclock()` and scheduler, waking the guest from `cpu_idle()`.
- In the AMD SVM handler, this timer injection was **omitted entirely**.

---

### 7. Whether ATOMS is currently delivering virtual interrupts to the guest.
- **Under Intel VMX (Physical Hardware)**: **YES**. Vector `0x20` is injected on `VMX_EXIT_REASON_HLT` when `IF=1`.
- **Under AMD SVM**: **NO**. The SVM handler only steps RIP; it does not write to the VMCB event injection field.
- **Under Fallback Step Loop**: **NO**.

---

### 8. Whether the repeated HLT exits are preventing FreeBSD from progressing toward device enumeration.
- **In QEMU under Fallback Loop**: **YES**, because the fallback loop does not execute the actual binary, but merely increments RIP across memory.
- **On Physical Hardware (Haswell / Raptor Lake)**: **NO**. Physical hardware does not use the fallback loop or AMD SVM; it runs pure hardware Intel VMX where the previous blocker was Exit 55 (XSETBV).

## 3. Architecture Defect Identification & Patch Plan

### Proven Defects:
1. **Defect 1 (AMD SVM HLT Handler)**:
   In `kernel/core/hypervisor/src/hypervisor.c` line 911, `case SVM_EXIT_HLT:` advances `guest_regs.rip += 1` instead of maintaining the halt state or injecting the timer interrupt.
2. **Defect 2 (Fallback Runtime Step)**:
   In `kernel/core/hypervisor/src/hypervisor.c` lines 2704–2713, the fallback loop unconditionally increments RIP by 1 on every tick, causing a 50,000 byte-per-second slide across kernel memory when hardware virtualization is not active.

### Architectural Solution (When Approved):
1. In `case SVM_EXIT_HLT:`, do **NOT** advance RIP. Check `RFLAGS.IF`; if `IF == 1`, inject LAPIC timer interrupt or yield, keeping RIP pointing at `HLT` until the interrupt arrives.
2. In the fallback runtime loop, do **NOT** advance `guest_regs.rip += 1`. Keep RIP steady at the guest entry point or halt address.
